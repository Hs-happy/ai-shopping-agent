# 面试问答：这个项目怎么讲

> 30 秒版本：一句话说明场景，一句话说明链路，一句话说明你解决的最难的问题。

**30 秒**：这是一个电商售前导购 Agent。用户说一句模糊需求，系统把它解析成结构化槽位，用 BM25 和向量两路召回五万条 SKU，RRF 融合后再重排，调 MCP 工具确认真实库存，最后用 SSE 把回答流式吐给前端。我主要解决了三个问题：槽位抽取的准确性、混合检索的顺序与置信度校准、工具超时的降级。

---

## 高频问题

### 1. 为什么要做混合检索，不能只用向量？

纯向量在电商场景有两个问题：一是型号、参数这类"精确 token"（`RTX 4060`、`16GB+512GB`）语义模型经常糊掉；二是新品、长尾商品向量空间里没有邻居，召回不到。BM25 正好补这两块。反过来纯 BM25 也解决不了"拍照好"到"影像旗舰"的语义跳跃。所以两路都要。

数据上也能看到：关键词型查询 BM25 recall 0.924、双路 0.889（略降）；语义型查询 BM25 只有 0.567、双路 0.700。线上模糊表达占多数，所以默认开双路，权重可配。

### 2. RRF 的 k 为什么取 60？

原论文的经验值，作用是平滑：k 越小，头部名次的优势越大；k 越大，长尾越容易浮上来。60 是个比较稳的中间值。我也试过 10 和 100，10 的时候两路排名靠前的商品互相压制，100 的时候第二路几乎变成均匀加分，效果都更差。这个参数在 `app/retrieval/fusion.py` 里可配。

### 3. 为什么先截断再重排？会不会漏？

会，所以顺序很重要，我们踩过坑。正确顺序是：**大池子召回（200/路）→ RRF → 硬约束过滤 → 截断 30 → 重排**。

最初的代码是"召回 30 → 过滤"，结果查"预算 2700 的拍照手机"时，池子里前 30 条全是 4000+ 的，过滤完是空的，只能放宽预算，最后推荐了 6699 的手机。改成先在大池子上过滤再截断后，这条查询的 recall 从 0 恢复到正常水平。

### 4. 置信度怎么算的？阈值怎么定？

三个分量加权：top1 重排分的绝对值（0.55）、top1 与 top2 的区分度（0.15）、前三条对硬约束的覆盖率（0.30）。

阈值 0.42 是拿评测集扫出来的：正常导购查询普遍在 0.55~0.8，无关问题（"帮我写一首诗"）在 0.33 左右，0.42 正好卡在中间。低于阈值触发一次 Query 改写 + 二次检索，还低就走澄清追问，不硬推。

一个坑：重排分最初用的是"批内归一化"，每次 top1 都是 1.0，置信度永远 0.9+，改写逻辑等于没写。改成绝对分之后才有区分度。

### 5. 槽位冲突怎么处理？

正则优先。价格、品牌这类硬字段，模型说错一个数字，后面全错，所以合并时用正则覆盖模型。语义属性（"拍照好" → 拍照）取并集。否定约束（"不要小米"）只增不减，并且在检索前置过滤里直接删掉，不参与打分。

另外两个多轮细节：品类切换要清空上一个品类的需求点（"降噪"对手机没意义）；"再便宜点"要真的把预算打七折，而不是只记一句话。

### 6. 工具为什么用 MCP？100ms 超时怎么做到的？

MCP 的好处是协议标准化，工具可以被别的 Agent 复用，不用给每个框架写一套适配。

100ms 的关键是**常驻子进程**：每次调用现起 Python 进程，光解释器启动就 300ms，超时就没意义了。所以 server 在应用启动时拉起，之后是 stdin/stdout 上的一问一答，一次调用 1~10ms。超时就标记 degraded，回退到商品库里的库存快照，并在回答里明确告诉用户"实时库存不可用"。

### 7. 没有 API Key 怎么跑？

LLM 是双模的：配了 key 走 OpenAI 兼容协议（DeepSeek/通义都行），没配就走确定性规则分支——槽位用正则、生成用模板。检索、工具、SSE 这些全是真实的，只有"生成"这一步换实现。这样 CI 里能断言全链路，不依赖网络和第三方服务。

### 8. 5 万条数据怎么来的？为什么还要"先脏后洗"？

合成的。规则按真实市场写：品牌只出现在对应品类，价格和规格强相关（旗舰才给 1TB、独显本才上 4060），卖点标签由规格反推。

"先脏后洗"是为了让 ETL 有真实工作量：价格混着 `￥4,999.00` / `4999元` / 整数三种写法，品牌有中英文别名，尺寸有"寸/英寸"两种，还有 3% 的重复铺货。ETL 洗掉 1740 条重复、107 条非法，剩 4.97 万。

### 9. 延迟怎么样？瓶颈在哪？

检索链路本身 4~5ms（BM25 1ms + 向量 2.6ms + 融合 + 重排），端到端主要花在 LLM 生成上。所以真要压延迟：一是流式输出让首 token 尽早出现，二是把重排截断在 30 条，三是工具并行。

### 10. 如果要上生产，你会怎么改？

- 检索换 ES（IK 分词）+ Milvus，`VectorIndex` / `BM25Index` 换成对应实现，pipeline 不动；
- 会话从 SQLite 换 Redis，加会话级限流；
- 工具调用加熔断器（连续失败 N 次直接短路）与缓存；
- 生成加内容安全审核与"不编造参数"的事实校验；
- 评测集扩到几百条，加人工标注的相关性分级。

## 可能被追问的细节

- **BM25F 的字段权重怎么定的**：标题 3.0（信息密度最高）、品牌+品类 3.0（强约束）、标签 2.0（人工/规则打的卖点）、规格 1.5、描述 1.0（噪声最多）。
- **为什么向量矩阵能用 numpy 暴力搜**：5 万 × 512 × 4B ≈ 100MB，一次全量点积 2.6ms，比网络调 Milvus 还快。10 万以上再考虑 ANN。
- **RRF 和加权求和的区别**：加权求和要归一化两路分数，BM25 十几分、余弦 0~1，权重很难调；RRF 只用名次，零调参。
- **多轮上下文存哪**：SQLite 的 sessions 表，每轮读写；没用 LangGraph 的 checkpointer 是为了跨进程恢复和审计。
- **怎么保证不胡编参数**：prompt 里给的是检索到的真实字段，并且明确禁止编造；没有 key 时模板直接拼真实字段。
